# FDE 工作站 · 评估与设计判断（evaluation）

> 日期：2026-11-03 ｜ 作者：Lead（多 agent 协作）｜ 状态：设计定稿
> 输入：①用户需求；②《AI Native 手册》（ainative.jubao.ai）；③dsh-superagent-prototype 仓库；④现有调研工作台实现与真实数据。
> 本文件回答「为什么这样设计、为什么不做另外几条路」，规格见 `01-spec.md`，实施见 `02-plan.md`。

## 0. 结论先行

1. **值得做，但不要重写成另一个 superagent。** 现有工作台的价值在方法、脚本、安全栈和 8 个真实客户卷；缺的是「客户经营的状态与编排」。把这三块拆开看，只有第三块需要新建，前两块应原样继承。
2. **superagent 的架构思想可迁移，代码不能直接装。** 它面向「一个 GitHub 仓库的主动 coding agent」，强绑定 0.2.1-alpha.2 + GitHub/Feishu Source + SQLite + TS 构建；本机是 0.2.0-rc.2 + 纯 JS link 插件 + 单机单人。直接安装的成本和风险都高于收益，正确姿势是借它的**工单/注意力/授权/报告**内核，用 1/20 的体量重写。
3. **《AI Native 手册》给的不是功能清单，是构建纪律。** 最有价值的三条：每阶段一份进仓库的产物 + 一个人工关卡；能机械判断的规则下沉成护栏并定期查行为；复盘→规则→hook 的进化回路。这三条同时用于「构建过程」和「工作站产品本身」。
4. **成败不在看板好不好看，在状态是否可信。** 如果看板上的阶段、下一步、门禁和磁盘产物对不上，第二天就没人看。因此 v1 把「单一事实来源 + 门禁检查 + 回报闭环 + 备份回滚」放在视觉之前。
5. **默认自主性是 observe，不是 auto。** 对客户经营这类高后果场景，agent 先建议、人再采纳；硬红线（推进阶段、过门禁、对外发送、删除）任何模式都不自动。

## 2. 现状问题诊断（有实测依据）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | 没有持久化经营状态 | 面板每次请求现扫目录、数 md（`docs/research/current-workbench.md` §1） | 阶段、优先级、下一步、注意力无法跨会话保持 |
| 2 | 阶段口径系统性偏低 | 8 个真项目 7 个 exports=0、4 个 proposal=0，但实际成果散在 `background/内部/共识工作纸/子专题`（同上 §6） | 看板若沿用会低估每个人 |
| 3 | 技能是死资产 | 插件 `skills/` 4 个 SKILL.md 无人注册，Harness 只扫 `.dsh/skills`（同上 §3） | 写了技能但模型看不到 |
| 4 | 会话派发是「一次性 prompt」 | handoff 只有 start/stage/export/qa 四种文本，无工单 ID/状态/回报（同上 §1.4） | 派活后无法追踪、无法闭环 |
| 5 | 无注意力概念 | 五页签全是「查看」，没有「现在要我做什么」 | 人要靠记忆驱动，漏事 |
| 6 | adoption 直接写盘、不可撤销 | `/adopt`、`/toproject` 往任意目录写档案与子目录（同上 §7.5-8） | 误操作风险 |
| 7 | 性能与并发隐患 | 双扫描、全树递归、轮询会放大（同上 §7.5-5） | 看板轮询会卡 |
| 8 | 体验缺口 | 无轮询、无深链、无拖拽、无错误态（同上 §2.2） | 「看板」名不副实 |

诊断结论：**不是功能少，是缺一个稳定的经营对象与一条可检查的推进流程。** 所以新建的重点是「状态 + 编排 + 闭环」，不是再加几个按钮。

## 3. 路线评估：superagent 怎么结合

### 3.1 三条路线

| 路线 | 做法 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| A 直接安装 | 把仓库作为 bundle 装进 profile（或降版本改造后安装） | 高：TS 构建、0.2.1-alpha.2 peer 依赖、SQLite、Source 配置、GitHub/Feishu 凭据 | 高：版本不兼容白屏/启动失败；场景不匹配；维护上游变更 | **不选** |
| B 源码裁剪移植 | 把 core/engine、effects、outbox、ticket 等 TS 移植成 JS | 高：约 1.5–2 万行；依赖 zod、proper-lockfile、SQLite、Session 编排 | 高：移植错一处状态机就错；测试成本巨大 | **不选（v1）** |
| C 设计借鉴 + 轻量重写 | 提取工单/注意力/授权/报告语义，用单文件 JSON + 现有路由/工具实现 | 中：约 1500–2500 行（宿主 + 面板） | 中：语义简化后要防走样 | **选它** |

选择 C 的判断依据：FDE 工作站是**单机、单人、低并发**的客户经营工具，不需要多 Source 事件流、多 Executor 调度、SQLite 事务和重启恢复全套；它的核心价值在「知道每件事卡在哪、下一步是什么、什么时候需要人」，而不是「高吞吐地自动接活」。用 1/10 的复杂度换 80% 的价值，是这个场景的正确取舍。

实测证据（详见 `docs/research/superagent-extract.md` §6）：
- 本机 DSH 0.2.0-rc.2，superagent 的 21/21 个 `@deepseek-ai/dsh-*` peer 要求 `^0.2.1-alpha.2`；用 DSH 自带 `evaluatePluginCompatibility()` 实测返回 incompatible，需 `dsh plugin allow-version ... --accept-risk` 豁免才可能挂载，而该命令警告「可能崩溃或损坏数据」。这不是 `pnpm add` 的 warning，是默认挂不上。
- 其依赖树会带入 `cordis@4.0.5-alpha.1`（本机 4.0.4）与 25 个 0.2.1-alpha.2 框架包、约 123MB，形成两套实例；官方支持形态是独立 DSH 0.2.1 profile，不是现网 profile 内的一个面板。
- 它的运行时要求 `danger-full-access`、接管 Session、改进程级 PATH 与 git 配置；与「在现有 GUI 里加一个看板」不是一个量级。
- 可复用的是判定表、授权不变量、效果队列语义与面板「三问」信息架构——零依赖设计资产，与版本无关。

### 3.2 概念映射：保留什么、改什么、扔什么

| superagent 概念 | FDE 映射 | 处理 | 理由 |
|---|---|---|---|
| Source（事件源） | 手工录入 / 目录扫描 / 会话回报 / 规则触发 | 保留思想，v1 只做 4 个轻量源 | 接 IM/邮件是 v2 的事；先保证状态可信 |
| Trigger（不可变事件） | activity / timeline 条目 | 简化 | 不需要幂等重放，保留审计即可 |
| Thread（时间线） | engagement.timeline | 保留 | 客户时间线是刚需 |
| Eval + Decision | 规则引擎 proposals | 简化 | 不做模型评估，只做确定性规则 + 人采纳 |
| Mandate（授权） | autonomy 模式 + 硬红线 | 保留思想，简化为三档 | 授权要可解释，不做 Mandate 版本 |
| Ticket（工单） | **item（任务） + engagement（客户）** | 拆成两层 | 客户是经营对象，任务是执行对象；superagent 只有一层 |
| Ticket stage | **两个状态机**：客户 7 阶段 + 任务 5 泳道 | 扩展 | 计划视图 vs 执行视图分离 |
| Assignment / Executor | handoff → DSH 会话 | 保留，轻量 | 复用现有 create+prompt，不做 worker slot |
| Report | item.report（progress/ready/blocked/failed/dropped） | 保留 | 闭环关键：agent 必须回报 |
| Attention | 派生 + 显式注意力 | 保留并强化 | 这是面板的核心信息架构 |
| Policy | settings + 硬红线 + 门禁 | 简化 | 单人场景不需要多主体授权表 |
| effects/outbox/SQLite | 单 JSON + 原子写 + 备份 | 丢弃 | 规模不需要；单机 JSON 可审计可回滚 |
| 面板多页 | 六视图 + 抽屉 | 借鉴信息架构 | 「只显示需要人的」变成「今日」页 |

## 4. 产品定义与边界

**FDE 工作站 = 客户经营的操作系统。** 它管三件事：
1. **经营状态**：每个客户在哪一阶段、下一步是什么、缺什么证据、谁在等谁；
2. **人的注意力**：哪些事现在必须由人决定/审阅/回答/解阻，其余不打扰；
3. **执行闭环**：从看板派活给 agent 会话，会话按阶段方法干活并通过工具回报，人审阅后推进。

**它不是**：CRM（不管金额预测/合同回款）、IM（不接群聊）、多 agent 调度平台（不复制 superagent 全套）、云端多用户系统（无账号/权限）、自动销售机器人（不自动对外）。

这个边界来自一个判断：**一个人的经营带宽有限，工具的价值是减少「找状态」和「记事情」的注意力消耗，而不是增加功能。** 功能越多、状态越难对齐，工作台就越会变成第二个待办清单。

## 5. 设计取舍记录

| # | 决策 | 放弃的方案 | 理由 | 代价 |
|---|---|---|---|---|
| D1 | 在现有插件内演进 | 新建 `@local/fde-workstation` 包 | 复用 12 条路由的安全栈、methods/scripts、profile link 安装链；避免重复资产与双入口 | 单文件变大；宿主改动仍需重启 |
| D2 | 状态用单 JSON（`research/.fde/board.json`） | SQLite / 多文件 registry | 可读、可 diff、可备份、可手工修复；单机数据量 < 1MB | 并发写弱；靠原子写 + CAS 兜底 |
| D3 | 客户与任务双实体 | 只做任务看板 / 只做客户看板 | 计划（客户生命周期）与执行（任务流转）是两个问题，混在一起会两边都不好用 | 数据模型与 UI 复杂度上升 |
| D4 | 门禁 = 自动检查 + 人工确认 | 纯人工 / 纯自动 | 自动项防「凭感觉」，人工项防「机器替人拍板」；允许 force 但留痕 | 推进阶段有摩擦（有意为之） |
| D5 | 规则只在读取时求值，无后台定时器 | 定时任务 / 常驻 watcher | 避免第二套自动引擎（手册铁律）；单机不需要秒级 | 不打开面板就不提醒（可接受） |
| D6 | 技能用 `ctx.skills.register()` 运行时注册 | 复制到 `.dsh/skills` | 单一来源、随插件升级、不污染用户目录 | 注册需重启宿主；服务缺失要降级 |
| D7 | 默认 observe，硬红线不可自动 | auto 优先 / 全自动 | 高后果场景先建议后执行；信任是逐步建立的 | 需要人多点几下（v1 可接受） |
| D8 | 面板「今日」优先于「看板」 | 看板作为首页 | 注意力比概览更重要；看板是计划工具，今日是执行工具 | 需要维护两套视图 |
| D9 | 不引入图表/统计 | 仪表盘 | 数据量小、统计会制造「看起来很努力」的幻觉 | v2 再看 |
| D10 | 不自动生成对外材料 | 一键出方案并发送 | 对外内容一次事故代价远高于省下的时间 | 仍需人工导出/发送 |

## 6. 关键机制为什么这样设计

### 6.1 为什么「门禁」是产品核心而不是限制
FDE 的失败通常是**在错误前提上做对了事**：主体锁定错了、证据是 C 级却写成事实、方案没写边界、试点没定成功指标。门禁把「什么时候可以往下走」变成可检查的产物清单，用摩擦换可信。手册的「每阶段一份产物 + 一个人工关卡」在客户经营里同样成立。

### 6.2 为什么注意力要「派生 + 显式」两层
派生（逾期/停滞/待审/门禁）保证不漏；显式（agent 提问、人标记）保证能主动升级。只做派生会漏掉机器不知道的事；只做显式会依赖人记得标记。两者合并、统一排序，才能做到「只显示需要人的」。

### 6.3 为什么回报必须走工具而不是读会话日志
读 Session 日志需要订阅事件、解析格式、处理重启恢复——成本高且易错。让执行会话在结束时调用 `fde_item report`，是人机之间最小、最稳的契约；v1 允许不回报（≥70% 闭环率是目标，不是强制）。

### 6.4 为什么单一事实来源要加测试
阶段名/顺序/门禁 key 会同时出现在 schema、路由校验、工具描述、提示词、面板五处。手册的坑卡（one-definition）说明这类分叉不会报错，只会悄悄不一致。因此定义只写一处（`fde-schema.js`），面板从 `/meta` 读，测试断言「客户端不含硬编码阶段顺序」。

## 8. 成本与收益

| 项 | 估算 |
|---|---|
| 代码量 | 宿主新增约 1500–2000 行（schema/store/rules/api/prompts/路由/工具/技能注册/测试）；面板重构约 1500–2200 行；技能与文档约 1800 行 |

| 收益 | ① 8 个项目统一进看板，经营状态可查；② 「今日」把每天要处理的事收敛到一屏；③ 会话派活→回报闭环；④ 技能真正可被模型加载；⑤ 门禁把「什么时候能往下走」变成可检查 |

## 9. 分期路线

**v1（本次）**：看板（客户 7 阶段 + 任务 5 泳道）、今日注意力、客户抽屉、门禁、任务回报、adopt 两段式、6 工具、9 技能、健康检查、兼容降级。

**v1.1（候选，按真实使用决定）**：
- 面板轮询与事件增量（若卡顿）
- bid-intel 作为 Source（招标公告命中客户 → 建议）
- 会话事件自动回报（减少 agent 忘记 report）
- 周报生成与导出
- 多工作区/多 owner

**明确不建议（至少半年内）**：SQLite 迁移、多用户权限、IM 接入、自动对外发送、图表仪表盘、把 superagent 整个装进来。

## 10. 数据缺口与未验证事项

- **未做真实浏览器验证**：本机 GUI 需要认证 URL，按验证纪律不索取/不使用凭据；面板只做了静态与运行时渲染检查。用户刷新页面后可自行确认，若异常按「重启宿主 + 贴控制台错误」排查。
- **宿主未重启前**，新路由不可用是预期行为；本报告中的「已验证」仅指单测与静态检查。
- superagent 的可行性判断基于其仓库 package.json（engines ^22.19、peerDependencies ^0.2.1-alpha.2）与本机 0.2.0-rc.2 对照；未实际尝试安装（按评估结论不必要，且安装会改 profile）。
- 手册的量化经验是单人单技术栈样本，不视为普适结论；本设计只迁移机制，不迁移数字。
- 8 个真实项目的「建议阶段」由规则推断，最终阶段由人确认；导入不自动改目录。

## 12. v1.1 追加：招采雷达并入（2026-11-03）

### 12.1 判断

招采雷达（`@local/bid-intel`）是已有独立插件（本地索引实测 24,208 条、5 个面板视图、6 个 agent 工具）。用户要求「并入 FDE 工作站」，正确做法不是合并代码或搬 42MB 数据，而是**让 FDE 多一个「客户经营的情报输入层」**：

- bid-intel 保持独立与单一数据源，新增只读 host 服务 `bidIntel`（`ctx.provide`，契约 version=1）；
- FDE 只做**客户关联层**：把公告按客户名称/简称/目录/关键词匹配（buyer/winner/candidate/mention），关联（link）、提升为跟进任务（promote），并用「近 30 天招标类公告」生成建议（bid_signal）；
- 全量检索/时间线/批次/成稿仍用 bid-intel 的 `bid_*` 工具，不新增第二套检索语义（ONE-DEFINITION）。

详见 `docs/adr/0002-bid-intel-integration.md`。

### 12.2 交付

| 层 | 内容 |
|---|---|
| 数据契约 | bid-intel 暴露 `bidIntel` 服务（version/dataMeta/stats/search/timeline/batches/report + getRecord）；FDE 懒取、版本校验、缺失即降级 |
| 匹配 | 查询词变体（全称/去括号/括号 token/去年份/短核心/关键词，≤8）；四类关系；tender/award 标记；按 id 去重；金额只展示原文；`total`（采样）与 `approxTotal`（量级）分开 |
| 状态 | `engagement.bidWatch {enabled, keywords, links, lastMatchAt}`；`item.bidRefs`；link/unlink/promote 走 CAS 事务、`by` 如实留痕 |
| 路由/工具 | 7 条 `/fde/bids/*` 路由；第 7 个工具 `fde_bid`（search/match/link/unlink/promote/timeline） |
| 信号 | `bid_signal` 规则：开关开 + 近 30 天 + 招标/采购/询价/谈判类 + buyer/mention；去重、dismissed 30 天、paused 跳过、pending≤8 |
| 面板 | 第 7 页签「招采」（概况/检索/结果/客户匹配概览/导入链接）；客户抽屉「招采雷达」区（徽章/Top5/加入跟进/关联/取消/刷新）；看板卡片「招采 N」；设置开关；服务不可用降级 |
| 技能 | 新 `fde-bid-radar`；fde-discovery/meeting/solution/board 增补；系统提示词加招采口径与「FDE 只做关联层」 |

### 12.3 实测（live，2026-11-03）

- 两个插件经 plugin_manager 重载后生效；`fde_bid` 出现在工具清单，10 个 FDE 技能出现。
- 某研究院客户 match：`approxTotal` 量级 1,730（含 mention）、采样 53 条、中标 28、最近 2026-10-16；查询词自动展开为「客户全称 / 括号内简称 / 全称+后缀」。
- `fde_bid search 某超算公司`（company）：6 条（直接 4 / 提及 2），展示中标人与金额原文，未求和。
- 0 命中客户（某军工科技公司等）优雅返回「相关 0」，不报错；此前已知索引以航发专区为主，0 命中是数据事实并已写入技能口径。
- 第三轮独立审计：`acceptance-audit` **450/450 全绿、P0/P1/P2=0**；`verify/all.mjs` 全绿。

### 12.4 限制

- 「相关 ≈N」中的 N 是各查询 `search.total` 的最大值，用于表示量级；采样列表按查询上限截断，**不是逐条对账的精确去重总数**（面板同时标注「采样 M 条」）。
- 匹配是确定性规则，不是语义匹配：名称差异大（简称/别名未收录）会漏；`bidWatch.keywords` 可人工补词。
- 数据覆盖以航发专区为主（24,069），其他平台合计约 141 条；数据缺口必须如实说明。
- 真实浏览器渲染、真实采集后缓存刷新、真实 handoff 的点选未在本机验证（同 v1 限制）。

### 12.5 结论

招采雷达以「服务桥接 + 客户关联层」并入，达到了用户要的「在工作站里看这家单位招过什么、谁中标、有没有新机会」，同时保留 bid-intel 的独立数据源与深挖能力。v1.1 可以交付；下一步若要做「招标机会 → 自动建任务」，需先把 bid_signal 在 assisted/auto 模式下的执行路径补成可审计的自动化（当前默认 observe，仅建议）。

### 13.5 限制（如实）

1. **GitHub 限流**：未认证每小时 60 次且与同 IP 共享；首版 30 仓库/天在限额内，失败降级保留旧值并显示 warning，不假装全绿。

3. **权重/费率/毛利率未验证**：12 维权重、35–50% 毛利率、5–20 万甜点区均为方法默认值/经验区间，需用真实项目校准（报价偏差率 = 报价 vs 实际成本）。
4. **面板未做真实浏览器页面级验证**：宿主需重载后生效；本轮在 node 层（静态/准运行时/契约）验证，未在已认证浏览器里点选。
5. **方法组仍小（8 条）**：首版以官方 cookbook/课程为主，后续按用户使用反馈扩充。
6. **P2 观察项（3）**：工件扫描 TTL 缓存签名不含子目录 mtime（存量）、`/fde/health` 未单列资料库检查（下轮可补）、`validateCatalog` 未软校验 `featuredRank`/`track` 上限（下轮可补 warning）。
