# 复盘（retro）模板与约定

> 用途：把一次经历变成**下次能机械执行的东西**。复盘不是汇报，失败、未完成、判断错误都要写。
> 依据：`docs/research/handbook-extract.md` §5.6（retro 骨架）与 §7.4（进化回路）。规则承载优先级：复盘文字 < playbook/runbook < hook/自动检查。

## 一、放在哪

| 复盘类型 | 放置位置 | 命名 |
|---|---|---|
| 单客户项目/会面/交付复盘 | 客户卷 `research/<客户>/` | `复盘-<YYYYMMDD>.md` |
| 跨客户的方法沉淀、插件/流程复盘 | 插件仓 `docs/retros/` | `<YYYY-MM-DD>-<事件>.md` |
| 事故复盘 | 插件仓 `docs/retros/`（涉及客户时客户卷另存脱敏版） | `<YYYY-MM-DD>-<事件>.md` |

判断只问一句：**这份内容会不会因为改代码而需要跟着改？** 会 → 代码仓（插件仓）；不会 → 客户卷/ops 侧。
两处都写时，客户卷放事实，插件仓放方法，互相链接，**不复制全文**。

## 二、模板骨架

```markdown
# 复盘：<事件>

- 日期｜类型（事故 / 项目 / 阶段 / 试用期评估）｜影响（谁、多大、多久）｜相关链接（spec/ADR/任务）
- 状态：草稿 / 已复盘 / 已沉淀

## 做了什么（按时间，事实，不带评价）

| 时间 | 动作 | 结果/证据（文件路径或命令输出） |
|---|---|---|

## 为什么这么做（当时的判断和依据，包括当时不知道的信息）

- 当时知道什么、不知道什么；为什么选这个方案、放弃了什么。

## 遇到了什么（时间线；根因一直问到环境和规则层面）

| 时间 | 现象 | 当时处理 | 根因（到规则/工具/环境层） |
|---|---|---|---|

## 下次怎么做

| 行动 | 负责人 | 截止 | 状态 |
|---|---|---|---|

## Harness 反馈（六类，逐类过，空的写「本次无」）

| 类别 | 这次的问题 | 改哪里（文件/命令/检查项） | 状态 |
|---|---|---|---|
| 导航 | | | |
| 自动检查 | | | |
| 规则与审查 | | | |
| 权限与护栏 | | | |
| 工具与开销 | | | |
| 信息获取 | | | |
```

### Harness 反馈六类怎么填

| 类别 | 管什么 | 例子 |
|---|---|---|
| 导航 | 找文件、找入口、找状态的成本 | 「看板状态散在多个 md，找不到唯一来源」 |
| 自动检查 | 能机械验证却靠人记的项 | 「面板改了没重新 build，靠人记得跑」→ 加进 `health-check.mjs` |
| 规则与审查 | 规则缺失、表述模糊、审查抓不到 | 「门禁 force 没要求 reason」→ 写进 REVIEW/测试 |
| 权限与护栏 | 越权、破坏性操作、回滚能力 | 「会手滑删客户目录」→ 加二次确认/备份 |
| 工具与开销 | 工具缺失、太慢、上下文太贵 | 「每次重读整份方法文件」→ 抽 checklist |
| 信息获取 | 抓不到、渠道不可用、误判 | 「web_fetch 全域名失败只能 curl」→ 写进 `reference/数据源清单.md` |

## 三、三条原则（来自手册）

1. **能机械执行的不要只写文字**：能变成检查项/hook 的，写进行动列并落到 `scripts/health-check.mjs`、`verify/` 或 `REVIEW.md`。
2. **同一个坑出现两次就起草 hook**：第二次出现时，行动项必须包含「自动检查」而不是再写一遍提醒。
3. **「改哪里」写不出文件名，说明这条还没想清楚**：写不出就先标「待定位」，别把模糊结论当真复盘。

## 四、提交前自检

- [ ] 时间线每条有出处（文件路径 / 命令输出 / board timeline / 会话）。
- [ ] 根因至少追到规则、工具或环境层面，不停在「某人粗心」。
- [ ] 行动项有负责人、截止、状态，且可检查（没有「加强沟通」）。
- [ ] Harness 六类逐类填过（空类写「本次无」）。
- [ ] 脱敏：客户真名 → 「某集团」；金额、人名、涉密细节不进插件仓。
- [ ] 已判断沉淀位置：客户卷事实 / 插件仓方法 / 规则更新建议（由人审后合入）。
