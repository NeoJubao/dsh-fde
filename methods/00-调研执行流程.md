# 00 · 调研执行流程（端到端七步）

> 输入：**公司全称 + 见面对象与职务 + 见面性质**
> 输出：会面 Brief / 研判底稿 / 合作地图 / 正式方案（含 PDF）

---

## 第 1 步｜立项（10 分钟）

1. 建项目目录：`projects/<公司简称>-<YYYYMMDD>/`，含 `raw/ research/ meeting/ proposal/`
2. 填 `00-项目档案.md`：记录输入三要素、目标、约束、至今已确认/未确认事项
3. 明确**本次要拿到的三个结果**（示例：锁定主体 / 拿到对接人 / 摸清在某个项目中的角色）

> ⚠️ 从第一步就记录"用户口述"与"公开事实"可能存在的差异——本次实践中，用户口述的集团名与实际主体不符，靠早期记录才没走偏。

---

## 第 2 步｜侦察与主体锁定（30–60 分钟）

**目标：先确定"对方到底是谁"，再研究"他怎么样"。** 顺序颠倒会全盘白做。

### 2.1 地址锚定法（最硬的锚点）

若已知见面地址：
1. 用地址反查主体：搜索 `"<地址>" + 公司/院/设计院`
2. 在候选主体的官网上核对**注册/办公地址**是否一致（要求 ≥2 处独立页面互证）
3. **排除同园区不同单位**——本次遇到同一栋楼 9/10 层属另一家单位，差点误判

### 2.2 工商与归属验证

| 手段 | 用途 |
|---|---|
| 官网"公司概况/关于我们" | 成立时间、隶属关系、规模——**一手** |
| 母公司官网"成员企业/组织架构" | 反向确认是否为子公司 |
| 集团成员企业**全部分页** | 本次发现前 5 页返回同一组 12 家，确认无分页遗漏 |
| 上市公司年报/债券报告合并范围 | 反向排除（"不在合并范围内"同样是证据） |
| 百度百科/天眼查/启信宝公开页 | 补充工商信息（注意 WAF 与登录墙） |

### 2.3 三链验证（归属结论必须三链）

1. **自述链**：子公司官网怎么说的
2. **上级链**：母公司官网是否列为成员企业
3. **排除链**：可疑的另一方名单里有没有它（含分页核验）

三条不一致时 → 结论标为"待现场确认"，并在材料中写明推理。

---

## 第 3 步｜信息抓取（1–3 小时）

### 3.1 通道选择（重要）

| 通道 | 适用 | 说明 |
|---|---|---|
| `scripts/grab.py` | **首选** | `curl` 直连 + 正文抽取，可绕过 `web_fetch` 的 SSRF 误判 |
| `web_search` | 发现入口、取摘要 | 用于找 URL，不用于取正文 |
| PDF 工具 | 政府文件、年报、规划 | `pdftotext -layout`；DOCX 用 zipfile 解 XML |

### 3.2 抓取优先级

1. **官网**：公司概况 / 组织架构 / 领导班子 / 新闻中心 / 招采公告 / 招聘
2. **招投标平台**：省公共资源交易、政府采购网、成德眉资专区——**找中标与采购记录**
3. **政府渠道**：政府公示的规划文件、国资委稿件、ESG/社会责任报告
4. **权威媒体**：专访类稿件常含**量化战果**与内部机制（如"书记领办项目"）
5. **招聘网站**：岗位 JD 与"紧缺急需岗"是**组织痛点与人才缺口的直接证据**

### 3.3 抓取证据链

- 全部原文落盘到 `raw/`，文件命名含来源与日期
- 每份材料记录：URL、抓取时间、关键原文句
- 抓不到的（412/403/登录墙）**如实标注，换来源**，不要卡在一个源上

---

## 第 4 步｜事实核查（1 小时）

执行 `01-事实核查协议.md`，产出 `research/事实核查清单.md`：
- 全部事实按 **A（原文）/ B（二手或推算）/ C（必须现场核实）** 三级分类
- **数字自检**：占比重算、分项求和、口径统一（本次发现占比错误 + 原规划残差）
- 输出"不得作为事实陈述"的 C 级清单

---

## 第 5 步｜KPI 与痛点假设（1–2 小时）

执行 `02-KPI与痛点假设法.md`，产出 `research/KPI与痛点假设.md`：
- 每位关键决策人 **5–10 条假设**，每条含：假设内容 / 置信度 / 依据（附来源）/ 推论 / **可提问验证的问法**
- 每条必须标注"**假设**"，未经确认不得当事实使用

---

## 第 6 步｜会面材料（2 小时）

产出三个层次（递进关系，不要只做一份）：

| 文件 | 篇幅 | 用途 |
|---|---|---|
| **Brief** | 3–5 页 | **打印带进场**：三句话记住这个人 / 核心判断 / KPI 假设前三条 / 开场逐字稿 / 必问问题 / 硬边界 |
| **合作地图** | 4–6 页 | 谈"做什么"时用：合作空间全景 / 机会矩阵 / 进入通道 / **边界纪律** |
| **研判底稿（完整版）** | 8–12 页 | 前一晚通读：对象画像、组织现状、KPI 假设全表、议程与话术、待核实清单 |

**角色不同，侧重不同**：
- 一把手 → 战略、资产、考核、示范效应
- 分管副总/总工 → 技术可行性与责任边界
- 执行层（部门/中心） → 场景、数据、工期、预算

---

## 第 7 步｜方案生成与交付（2–4 小时）

1. 按 `skills/proposal-forge/SKILL.md` 的正式体例撰写
2. **需要多版本时**（本次实践经验）：
   - 先写"通用版"，再 `cp` 派生变体，**只改差异章节**——保证技术口径完全一致
   - 变体差异必须在版本对照文件中写明
3. 用 `scripts/make-pdf.sh` 导出 PDF，并执行**版面自检**（见脚本说明）
4. 版本归档：被取代的旧稿移入 `superseded/`，不留在交付目录

---

## 附：时间预算参考（首次调研）

| 步骤 | 耗时 |
|---|---|
| 立项 + 侦察 + 主体锁定 | 1–1.5 小时 |
| 抓取 + 证据落盘 | 2–3 小时 |
| 核查 + 假设 | 2 小时 |
| 会面材料 | 2 小时 |
| 方案 + PDF | 2–4 小时 |
| **合计** | **约 1 个工作日** |

**第二次做同类客户可压缩至 3–4 小时**（因为知识库与脚本已沉淀）。
