# 方案生成与 PDF 导出技能

> **定位：本技能是方法库，由 `fde-solution` 编排，不要独立自动触发。**
> 需要按客户阶段出方案、定版本、回报门禁时先用 `fde-solution`；本技能只提供骨架、多版本与导出的具体做法。正式对外交付见 `methods/05-正式对外文档交付（DOCX·公文版式）.md` 与 `fde-delivery`。

> 输入：调研材料（事实核查 + 合作地图 + 实施设想）
> 输出：正式方案（Markdown + PDF），必要时多版本

---

## 一、正式方案与内部材料的区别（关键）

| 维度 | 内部材料 | **正式方案** |
|---|---|---|
| 人称 | "我们"、"对方"、话术 | **无第一人称主观表述**；用"本方案建议……" |
| 结构 | 按沟通顺序 | 按**标准方案体例**（背景→现状→目标→架构→场景→实施→投资→成效→保障） |
| 结论 | 策略、打法 | **分析 + 依据**，结论自然得出 |
| 推测 | 假设、置信度 | **删除或改写为"待明确事项"** |
| 数据 | 可用 B 级 | 尽量 A 级；计算值标明；**原文件矛盾如实标注** |
| 口吻 | 说服性 | **克制、可被审查** |

**转换三原则**：
1. **结论改写成分析**——把"钱在哪 AI 就该挂在哪"改写成"投资结构表 + 投资结构建议"三条
2. **删除内部视角**——话术、竞争判断、KPI 假设、策略不进正文
3. **每项建议都留余地**——"具体以立项文件为准""须与主管部门共同确认"

## 二、标准章节骨架（建设方案类）

```markdown
# <项目名>建设方案
（封面信息表：文件名称/版本/编制单位/日期/文件性质）

## 摘要
## 一、项目背景与政策依据
   （政策部署 / 行业与地方规划 / 与上位平台关系）
## 二、区域现状与需求分析
   （现状数据 / 基础设施 / 能力缺口 / **项目基础与实施条件**）
## 三、建设目标与总体思路
   （目标 / 原则 / 技术依据）
## 四、总体架构
   （分层架构图 + 各层建设内容与边界）
## 五、应用场景建设内容
   （每场景统一字段：响应缺口/建设内容/数据前提/交付形态/可检查指标/**责任边界**）
## 六、实施路径
   （分阶段 + 决策门 + 实施程序 + 职责分工 + **工作界面** + 时序约束）
## 七、投资估算与资金安排
## 八、预期成效
## 九、组织保障与风险管理
## 十、交付成果与后续工作
## 附录：主要依据文件
```

**必备的三个"严谨性要素"**（最容易被评审追问）：
1. **责任边界**——AI 做什么、不做什么，谁签发
2. **工作界面**——数据/成果/责任/交付四条界面的界定
3. **决策门**——每阶段继续/调整/终止的条件

## 三、分阶段设计的铁律（本次踩过的坑）

**不要用软件开发节奏排政府/国企项目。** 必须计入：

| 必计项 | 影响 |
|---|---|
| **立项与财政评审** | 前置 1–3 个月 |
| **采购招标周期** | 政府项目 2–3 个月 |
| **数据授权协商** | 多部门时是关键路径 |
| **试运行期** | 通常不少于 3 个月 |
| **季节性约束** | 如汛期不得首次上线防汛模块 |
| **财年节点** | 跨年项目须完成阶段验收与结算 |

**输出要求**：
- 每阶段给出**周期区间**、**主要内容**、**阶段成果**、**决策门**
- 提供**总体节奏**（如首批 12–18 个月）与**甘特示意**
- 明确标注"周期为经验建议值，须与主管部门共同确认"

## 四、多版本管理（本次实践）

当需要"含 X 版"和"不含 X 版"时：

```bash
# 1) 先写通用版（完整）
# 2) 复制派生变体
cp 方案-通用版.md 方案-XX版.md
# 3) 只修改差异章节（用 edit 精确替换，不要整体重写）
# 4) 记录版本差异到 internal/交付版本对照.md
```

**原则**：**共性章节完全一致**（避免出现两套技术口径），差异只在组织、分工、衔接等章节。

**版本差异应记录**：文件名 / 定位 / / 差异章节 / 适用场景。

**版本归档**：被取代的旧稿移入 `superseded/`，不留在交付目录。

## 五、格式约定与 PDF 导出

### 5.1 约定：md 是主格式，PDF 按需导出

| 规则 | 说明 |
|---|---|
| **方案先写 md** | md 是**唯一事实来源**，所有修订只改 md |
| **PDF 按需** | **仅在要递交/汇报/打印时导出**；内部讨论与迭代阶段不导出 |
| **多版本** | 两版都定稿后各导一次；旧稿移入 `superseded/` |
| **不手改 PDF** | 改 md 后重跑命令重新生成 |
| **导出物归集** | PDF 默认输出到 md 同级的 `exports/`，工作目录只留 md |

### 5.2 导出命令

```bash
bash scripts/make-pdf.sh "<markdown 文件>"
```

脚本做的事：
1. `md2html.py`：Markdown → 带正式排版的 HTML（中文字体、A4 页边距、表格样式）
2. `weasyprint`：HTML → PDF

### 脚本已内置的排版修复（都是踩过的坑）

| 问题 | 处理 |
|---|---|
| 中文短标签被逐字断行（"响应缺口"→"响应缺/口"） | 第一列识别为**标签列**，短标签 `nowrap`，取消 `width:1%` 收缩 |
| 首列长文本（法规名）被压成多行 | 自动识别长文本列，给 42% 列宽 + 小一号字 |
| 列表末尾分号孤行 | 生成时统一转为句号 |
| 表格跨页断开 | `page-break-inside: avoid` |
| ASCII 架构图折行 | 等宽字体 + `white-space: pre` |

## 六、交付前自检（必做）

### 内容层
| # | 检查项 |
|---|---|
| 1 | 数字自检：占比重算、分项求和、口径统一 |
| 2 | 全部主观表述是否已清除（"我们/对方/话术/策略"） |
| 3 | 每个场景是否有**责任边界** |
| 4 | 分阶段是否含**决策门**与**程序** |
| 5 | 投资与指标是否留有"以立项文件为准"的余地 |
| 6 | 待明确事项是否单列 |

### 版面层（对 PDF 逐项验证）
```bash
pdftotext -layout out.pdf /tmp/o.txt
pdfinfo out.pdf | grep -E "Pages|Page size"      # 页数与规格
grep -cE "^\s*[\u4e00-\u9fff]{1,2}\s*$" /tmp/o.txt   # 孤行数（应为 0）
grep -nE "响应缺\s*$|建设内\s*$" /tmp/o.txt            # 拆标签（应为空）
python3 -c "t=open('/tmp/o.txt').read(); print('缺字:', '□' in t)"  # 应为 False
```

**建议再抽 2–3 页渲染成图目视确认**（封面页、含架构图页、含表格页）。

---

## 七、红线

1. **不美化原始数据的矛盾**——原文件自身有残差就如实标注
2. **不删除"未证实"标注**——正式方案里的待明确事项是专业性的体现，而非缺点
3. **不承诺能力边界之外的事**（如全自动出图、替代专业判断）
4. **不与已有系统/内部单位重复建设**
