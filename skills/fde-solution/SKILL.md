# fde-solution · 方案与多方分工

> 定位：把调研事实与 KPI 假设转成**可被审查的方案**：背景→现状→目标→架构→场景→实施→投资→成效→保障；每项建议都留余地，边界纪律必写。写法细节在 `proposal-forge`、`domain-model-partnership`（方法库）与 `methods/03`。
> 铁律：**内部材料 ≠ 正式方案**——正式方案删除主观视角与话术，结论改成分析，推测改成「待明确事项」。方案里必须含**成本测算与报价单**（`solution` 门禁的 `cost`/`quote` 自动项）；报价用 `fde_quote` 算、由人复核确认，**不构成对外报价**。

## 一、触发时机

- 「出个方案」「整理成正式方案」「做一版给客户看」。
- 客户进入 `solution` 阶段，门禁缺 `proposal/` 下 md 或「不做什么/边界」章节。
- 需要「含 X 版 / 不含 X 版」多版本，或要设计领域大模型的多方分工。
- 「方案评审要压成 10 页」→ 保留严谨性三要素，删展开细节，不删边界与口径。
- 方案是长文（≥5 节），或要「一页纸 / 一页摘要 / 传阅版」→ 另出一页纸（brief，加载 `longdoc-brief` 技能）。
- 「这个大概多少钱」「怎么报价」「客户要总价/分期」→ 走 `methods/07` + `fde_quote`，产出成本测算与报价单。
- 报价前要确认场景与范围已定（`scoping` 门禁已过）→ 没有范围就没有可报价的基线。
- 要历史成交价区间/竞争格局/对手中标记录 → 用 `fde-bid-radar` 取采购证据（金额只引原文）。
- 不触发：会面 Brief（`fde-meeting`）、试点设计（`fde-pilot`）。

## 二、输入

| 输入 | 必填 | 说明 |
|---|---|---|
| 事实核查清单 | 是 | 数字与结论的来源；A 级优先 |
| KPI 与痛点假设 | 是 | 决定方案主线与成效口径 |
| 合作地图 | 是 | 按客户业务方向分组的合作机会 |
| 边界纪律 | 是 | 不做对方已有的、不碰内部单位、不超责任承诺 |
| 用途与版本要求 | 是 | 内部讨论 / 正式对外 / 汇报；是否多版本 |
| 历史招采记录（可选） | 否 | `fde_bid`/`bid_search`：同类项目中标人与成交价原文，用于校准投资与竞争判断 |
| 场景与范围边界 | 是 | `scoping/范围与边界.md`：报价的输入；未定范围先回 `fde-scoping` |
| 定价配置 | 是 | `reference/fde-pricing.json`（费率卡/默认值/免责声明，可编辑） |

## 三、执行步骤（逐条可检查）

1. **定用途**：先问「这份给谁看、要不要递交、是否定稿」。检查：版本用途写进文件头（文件性质/版本/日期），不是口头默认。
2. **套骨架**：标准建设方案章节——摘要 / 背景与政策依据 / 区域或单位现状与需求 / 目标与思路 / 总体架构 / 应用场景 / 实施路径 / 投资估算 / 预期成效 / 组织保障与风险 / 交付成果。检查：章节顺序与骨架一致，缺章节要说明原因。
3. **每场景写全**：响应缺口 / 建设内容 / 数据前提 / 交付形态 / 可检查指标 / **责任边界**。检查：没有场景缺「责任边界」与「可检查指标」。
4. **写三个严谨性要素**：责任边界（AI 做什么、不做什么、谁签发）、工作界面（数据/成果/责任/交付四条）、决策门（每阶段继续/调整/终止条件）。检查：三者都能在正文定位到。
5. **分阶段排期**：政府/国企项目必须计入立项与财政评审、采购招标周期、数据授权协商、试运行期、季节性约束、财年节点；每阶段给周期区间、主要内容和阶段成果，并注明「经验建议值，须与主管部门共同确认」。检查：没有按纯软件开发节奏排的排期。
6. **投资与口径**：估算 / 控制价 / 成交价分开写；分项求和校验；主观表述清除（「我们/对方/话术/策略」不进正文）；待明确事项单列。检查：数字自检逐项过，正文无第一人称内部视角。历史成交价取招采原文（`fde-bid-radar`），只作区间参考，不换算、不求和、不当作本项目报价依据。
7. **成本测算（必做）**：按 `methods/07` 列 10 类成本（人力/数据评测/云 token/合规/运维/差旅/预备费/税/渠道/质保），用 `fde_quote` 算三点估算 P50/P80、成本合计、底线/目标/上限；落 `proposal/成本测算表.md`。检查：AI 四项（数据评测/云 token/合规/运维）无漏列；工具 `warnings` 逐条处理或写明接受理由。
8. **报价单与 SOW（必做）**：按 12 项报价单结构与 SOW 12 章写 `proposal/报价单.md`——in/out-of-scope、交付物、里程碑付款、价格明细与含税口径、假设与客户责任、除外、变更单、验收质保、有效期。检查：报价单金额与成本表可勾稽；对外报价由人复核确认，agent 不自称已报价。
9. **多版本管理**：先写通用版，再 `cp` 派生变体，只 edit 差异章节；共性章节完全一致；版本差异记到 `internal/交付版本对照.md`；旧稿进 `superseded/`。检查：两版技术口径没有分叉，差异表存在。
10. **落盘与回报**：写 `proposal/` 下 md → `fde_item {action:'report', kind:'ready', text:≤300字, artifacts:[路径]}`；`solution` 门禁的人工项 `solution_final`（可对外定稿）与 `pricing_confirmed`（成本报价已复核）**留给人确认**。检查：没有自行对外发送、没有自行勾选门禁。

11. **对客版本自检**：交给客户/领导前逐项过——数字可回算、无内部视角、无未确认人名、无越界承诺、待明确事项齐全、费率/毛利/合规费用已标「经验区间/方法默认值」。检查：缺一项就不提交，改完再过一遍。
12. **长文配一页纸（brief）**：方案 ≥5 节时，加载 `longdoc-brief` 技能，产出 `proposal/exports/方案-brief.html`（阅读版）与 `方案-brief-传阅版.html`（传阅版）。检查：一页纸含一句话结论、3 个关键数、判断表、建议、拍板事项、风险 top 3；一页打印验过；默认内部传阅，不随正式件外发。

| 产物 | 路径 | 命名规则 |
|---|---|---|
| 正式方案 | `research/<客户>/proposal/方案-<版本或日期>.md` | 文件名含版本或日期 |
| 成本测算表 | `research/<客户>/proposal/成本测算表.md` | 10 类成本 + 三点估算 + 预备费 + 勾稽 |
| 报价单 / SOW | `research/<客户>/proposal/报价单.md` | 12 项结构；含税口径、out-of-scope、变更、有效期 |

| 版本差异表 | `research/<客户>/internal/交付版本对照.md` | 版本 / 定位 / 差异章节 / 适用场景 |
| 历史稿 | `research/<客户>/proposal/superseded/` | 被取代的旧稿，不删 |
| 按需导出 | `research/<客户>/proposal/exports/` | 仅明确要求时生成 |
| 方案一页纸 · 阅读版 | `research/<客户>/proposal/exports/方案-brief.html` | 长文 ≥5 节必出；摘要，不是目录 |
| 方案一页纸 · 传阅版 | `research/<客户>/proposal/exports/方案-brief-传阅版.html` | A4 单页；默认内部传阅 |
| 多方分工一页纸 | `research/<客户>/meeting/三方分工建议（一页纸）.md` | 六层表 + 「都不做什么」 |

## 五、边界（不做什么）

- 不主动导出 PDF/DOCX；对外正式件只在人确认定稿后按 `methods/05` 处理。
- 不夸大成效指标；没有基线就不写「提升 X%」；估算标注为估算。
- 不承诺资源、价格、工期；不替代客户做立项与采购决策。
- 不报无依据价：成本表缺项、场景范围未定、token 单价未现查时先补，不拍数字；不把「估算/控制价/成交价」混写。
- 不把费率、毛利率、合规费用写成行业标准；一律标「方法默认值/经验区间，待验证」。
- 不与客户已有系统/下属数智单位重复建设；不替客户对外发送方案。
- 我方与模型方分工时，不把「只谈模型层」当方案；六层摊开再谈分工。
- 不把「合作意向」写成「已达成合作」；未签的都不算。
