# 会面材料准备技能

> **定位：本技能是方法库，由 `fde-meeting` 编排，不要独立自动触发。**
> 需要按客户阶段准备会面材料、落盘并回报时先用 `fde-meeting`；本技能只提供结构与写法细节。研判底稿的前置调研见 `fde-discovery`。

> 输入：客户 + 见面对象与职务 + 见面性质（初次拜访/方案汇报/谈具体项目）
> 输出：**Brief（现场用）+ 研判底稿（完整版）+ 合作地图**

---

## 一、三层材料（递进关系，不要只做一份）

| 层 | 文档 | 篇幅 | 使用时机 |
|---|---|---|---|
| 1 | **Brief** | 3–5 页 | **打印带进场**：60 秒可读完 |
| 2 | **合作地图** | 4–6 页 | 谈"做什么"时摊开 |
| 3 | **研判底稿（完整版）** | 8–12 页 | 前一晚通读 |

**逻辑**：Brief 决定**怎么开口** → 合作地图决定**谈什么** → 完整版支撑**追问**。

---

## 二、按对象层级调整侧重（关键）

| 对象 | 关心 | 材料侧重 | 禁忌 |
|---|---|---|---|
| **董事长 / 一把手** | 战略落地、经营指标、资产、示范效应、风险 | 判断 + 合作地图；面试式提问 | 不谈技术细节、不报价 |
| **分管副总 / 总工** | 技术可行性、责任边界、质量安全 | 方案架构、边界与制度、验收口径 | 不空谈战略 |
| **院长 / 部门负责人** | 产能、成本、成果可上报 | 场景清单、KPI 映射、实施路径 | 不讲集团概况 |
| **执行层** | 场景、数据、工期、谁配合 | 实施细节、分工与接口 | 不越级承诺 |

> **同日多场会面必须分别重做材料**，不能一份通用。

---

## 三、Brief 的标准结构（照此写）

```markdown
# <客户> <对象> · Brief

## 〇、三句话记住这个人        ← 履历特征 + 他推动过的事 + 当前工作重心
## 一、核心判断（决定怎么谈）    ← 一段话结论 + 我方只讲哪两件事
## 二、★ KPI 假设（前三条）      ← 表格：假设/置信度/依据/怎么说
   （其余假设折叠为备查表）
## 三、开场逐字稿（60–90 秒）    ← 可直接照读
## 四、三个入口                  ← 基于对方回答挑 1–2 个
## 五、必问五题
## 六、硬边界（3 条）
## 七、收尾（一定要拿到什么）
## 八、速查数据（备查，不必主动说）
```

**要点**：
- 开场必须**先说出对方已做成的事**（证明做了功课 + 表明不重复建设）
- 必须有**"闭嘴记录"**的提示
- 必须有**硬边界**（我们不做/不提什么）
- 必须写明**当场要拿到什么**（对接人/路径/时间）

## 四、完整版底稿的标准结构

```markdown
## 一、本次会面的定位与目标     ← 会面性质判断 + 三个必达目标
## 二、对方是谁：公开画像        ← 履历/任期/特点 + 公开动作轨迹（含解读）
## 三、组织在<议题>上的现状       ← 已有能力（不得重复建议）+ 战略定位 + 财务
## 四、★ KPI 与痛点假设         ← 全量假设：依据/推论/含义/验证问法 + 汇总表
## 五、合作入口（三条互补路径）
## 六、会谈议程建议（含逐字稿）   ← 时间分配：请教占一半以上
## 七、风险与边界（纪律清单）
## 八、待核实事项（C 级清单）
```

**议程时间分配原则**：**请教的时间应占一半以上**。层级越高，越应该让对方讲。

## 五、开场逐字稿模板

```
"<称呼>，我了解到<对方已做成的一件具体的事——带数字>。所以<我们不做什么>，这几件事我一句都不提。

我注意到<对方当前的某项工作重心>，我们想争取的是<互补定位>，不是来推销<某类产品>的。

具体就两件事：一是<具体的入口/机制>，我们想按<对方既有通道>来；二是<第二个入口>。
这两件事都不占<对方某项稀缺资源>。"
```

**然后闭嘴记录。**

---

## 六、硬边界的写法

必须包含三类：

| 类型 | 示例 |
|---|---|
| **不做对方已有的** | 不建平台、不做数据底座、不新建算力 |
| **不碰对方内部单位的地盘** | 不与对方下属数智公司竞争，不越过它直接对接 |
| **不做超责任承诺** | 不承诺替代专业判断与决策签发 |

## 七、质量自检

| # | 检查项 |
|---|---|
| 1 | Brief 是否能在 60 秒内读完并抓住重点？ |
| 2 | 开场是否引用了对方**具体做过的某件事**？ |
| 3 | KPI 假设是否**全部标注置信度与依据**？ |
| 4 | 是否有**"不做什么"**的硬边界？ |
| 5 | 必问问题是否覆盖"**摸清角色/找到通道/确认边界**"三类？ |
| 6 | 是否写明当场要拿到的具体结果？ |
| 7 | 称谓是否已确认（未确认时是否用了中性称呼）？ |

---

## 八、格式约定（md 为主，PDF 按需）

| 规则 | 说明 |
|---|---|
| **所有材料先写 md** | Brief / 合作地图 / 研判底稿**全部以 md 为主格式**，这是唯一事实来源 |
| **PDF 按需导出** | **仅在会面当天要打印带进场、或要发给对方时才导出**；日常修改只改 md |
| **不要预先生成** | 内容还会改，预生成的 PDF 只会过期；出门前统一导一次即可 |
| **导出到 exports/** | `bash scripts/make-pdf.sh "<文件>.md"` 默认输出到 md 同级的 `exports/` 子目录，并自动版面自检（致命问题应为 0、缺字应为「否」） |

**修 md → 重导 PDF，不要手改 PDF。**
